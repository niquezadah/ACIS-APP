# ACIS — Revisión por rúbrica

**Antes de editar o recomendar**: leer `references/RUBRICA_Y_CASO.md`. Prioridad de fuentes: (1) pauta/rúbrica oficial, (2) caso ACIS, (3) explicaciones/capturas del profesor, (4) repo real, (5) documentación oficial, (6) propuestas propias. Diferenciar expresamente **obligatorio**, **observado en clases**, **propuesto** y **comprobado**.

## Proceso obligatorio

1. Indicar criterio(s) IE afectado(s), peso y prueba esperada. No prometer nota.
2. Examinar evidencia en el código y la ejecución; separar **existe código** de **funciona en teléfono**. Si falta evidencia, marcar pendiente.
3. Priorizar tareas obligatorias de la evaluación sobre funciones opcionales; no agregar características a la app solo por creatividad.
4. Si una condición pertenece al *caso final* (p. ej. sincronización al recuperar señal / meteorología) y no se demostró que sea exigible a esta entrega parcial, indicar esa diferencia; no ocultar el requisito del caso.
5. Antes de cerrar tarea, definir prueba reproducible y qué evidencia conservar (captura, build, prueba, commit, tarjeta Trello).
6. Al final, describir: **criterio / modificación / verificación realizada / pendiente o riesgo**.

## Restricciones críticas

- Entrega colaborativa en parejas: GitHub público, README completo, contribuciones y planificación real en Trello; cumplir requisitos AVA y congelamiento del repo tras la fecha límite.
- No atribuir pruebas de emulador al Motorola; no declarar sincronización remota porque existan datos SQLite locales.
- No reemplazar reglas de la pauta por opiniones o links externos; el material original del punto 5.1 del caso llegó truncado.
- No confundir el proyecto inicial `com.example.acis` con el proyecto compartido `cl.acis.app`.
